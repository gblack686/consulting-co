# Overstory Expert

## Domain Overview
Overstory is a multi-agent orchestration system that turns a single Claude Code session into a coordinated team of worker agents. No separate daemon — your Claude Code session IS the orchestrator. It uses instruction overlays, tool-call guards, SQLite-based mail, and git worktrees via tmux to coordinate autonomous agents.

## Expert Type
**Domain Expert** - Deep expertise in Overstory CLI, agent fleet management, merge resolution, inter-agent messaging, runtime abstraction, and multi-agent orchestration patterns.

## Core Insight
> **Key Insight**: Overstory's innovation is that there is no separate daemon. The orchestrator IS the Claude Code session. Agents are spawned in git worktrees via tmux, communicate through typed SQLite mail, and merge results through a 4-tier conflict resolution system. The system is runtime-agnostic — it can orchestrate Claude, Pi, Copilot, Codex, Gemini, Sapling, and OpenCode agents.

## Key Capabilities
- **9 Agent Roles**: Coordinator, Orchestrator, Lead, Scout, Builder, Reviewer, Merger, Supervisor (deprecated), Monitor
- **5 SQLite Databases**: Sessions, Mail, Merge Queue, Events, Metrics (all WAL mode)
- **4-Tier Merge Resolution**: Clean → Auto-resolve → AI-resolve → Reimagine
- **3-Tier Watchdog**: Mechanical (Tier 0) → AI Triage (Tier 1) → Monitor Agent (Tier 2)
- **7 Runtime Adapters**: Claude, Pi, Copilot, Codex, Gemini, Sapling, OpenCode
- **35+ CLI Commands**: init, sling, status, merge, mail, dashboard, inspect, doctor, costs, etc.

## Architecture

### Agent Hierarchy
```
Orchestrator (your Claude Code session at project root)
  +-- Coordinator (persistent orchestrator in tmux)
  |     +-- Leads (team leads, depth 1)
  |           +-- Specialist Workers: Scout, Builder, Reviewer, Merger (depth 2)
  +-- Direct Workers (scout, builder, reviewer for simple tasks)
```

### Two-Layer Instruction System
- **Layer 1 (Base)**: Reusable `.md` files in `agents/` defining HOW (workflow, constraints)
- **Layer 2 (Overlay)**: Per-task `CLAUDE.md` generated by `ov sling`, injected into worktree, defining WHAT (task scope, file restrictions)

### Key Patterns
- **ZFC Principle**: Observable state (tmux alive, PID alive) is source of truth, not assumptions
- **Zero npm Runtime Dependencies**: Only 3 deps (chalk, commander, mulch-cli)
- **No `any`**: `noExplicitAny`, `noUncheckedIndexedAccess`, strict mode
- **Real Testing**: Never mock what you can use for real (real fs, real SQLite, real git)
- **Instructions as Markdown**: Agent definitions are `.md` files, not JSON/YAML DSL
