## Prompt 2: Framework Question (Intermediate)

**Question**: Explain the PITER framework and how it enables AFK agents.

**Response**:

### The PITER Framework

PITER is the framework for building AFK (Away From Keyboard) agents - systems that run while you're not there.

| Letter | Element | Implementation |
|--------|---------|---------------|
| **P** | Prompt Input | GitHub Issues |
| **T** | Trigger | GitHub Webhooks |
| **E** | Environment | Dedicated isolated environment |
| **R** | Review | Pull Requests + Observability |

**How Each Element Works**:

#### P - Prompt Input via GitHub Issues
Use GitHub issues as the input mechanism for your AFK agents. This allows you to trigger workflows from your phone, Slack, or anywhere you can create issues. The issue becomes the prompt.

#### T - Trigger via GitHub Webhooks
When a new issue is created, the webhook automatically kicks off your AFK agent workflow. No manual intervention required - the system responds to events.

#### E - Dedicated Environment
Your AFK agents need their own dedicated, isolated environment to run in. This ensures safe execution without interfering with your main development setup. Options include:
- Git worktrees
- Docker containers
- Agent sandboxes (E2B)

#### R - Review via Pull Requests
After your AFK agent completes its work, it creates a PR for review. This gives you visibility and control over what gets merged while maintaining the autonomous workflow.

**The Result**: From prompt input to merged PR automatically. The agent executes the entire workflow - classification, planning, implementation, and review - without your direct intervention.

**Related to Tactic #4**: Stay Out The Loop - Build systems that let your product build itself.

## Prompt 3: Pattern Question (Advanced)

**Question**: What are the three agent patterns (Pong, Echo, Calculator) and when should I use each?

**Response**:

### The Three Agent Patterns

From `building-specialized-agents/loot.md`:

#### 1. Pong Agent Pattern (Request-Response)

**Type**: Simplest custom agent
**Purpose**: Demonstrates total system prompt control

**When to Use**:
- Simple request-response workflows
- When you need to override the system prompt completely
- Creating an entirely new product experience

**Key Characteristics**:
- Override the system prompt to create a new product
- No custom tools needed
- Single-purpose focused execution

**Warning**: When you override the system prompt, this is NOT Claude Code anymore. You've created a new product entirely.

---

#### 2. Echo Agent Pattern (Event-Driven)

**Type**: Custom tool-enabled agent
**Purpose**: Add custom tools using the @tool decorator

**When to Use**:
- Event-driven workflows
- When you need specialized capabilities beyond default tools
- Building MCP servers in-memory

**Key Characteristics**:
- Uses @tool decorator to add custom tools
- Tool description tells agent how to use it
- SDK MCP servers created in-memory

**Example**: An agent that listens for events and responds with custom actions.

---

#### 3. Calculator Agent Pattern (Tool-Heavy)

**Type**: Focused functionality agent
**Purpose**: More capable custom agents with specific toolsets

**When to Use**:
- Tool-heavy workflows (many specialized operations)
- When you need focused functionality
- Domain-specific problem solving

**Key Characteristics**:
- Uses consistent codebase architecture
- Strips unnecessary tools (default Claude Code has 15+ tools)
- Maximum context efficiency

**Warning**: 15 extra tools consume space in your agent's mind. Use `/context` command to understand what's going into your agent.

---

### Pattern Selection Guide

| Scenario | Pattern | Reason |
|----------|---------|--------|
| Simple Q&A | Pong | Request-response is sufficient |
| Webhook handler | Echo | Event-driven with custom actions |
| Data processing | Calculator | Heavy tool usage, focused scope |
| Code review | Calculator | Needs specific tools, clear purpose |
| Chat interface | Pong | System prompt defines behavior |

### ADW Workflow Types

|------|-------|------|

| `plan_build_review` | 3 | /plan → /build → /review |
| `plan_build_review_fix` | 4 | /plan → /build → /review → /fix |

---

### plan_build (2 Steps)

**Flow**: `/plan` → `/build`

**When to Use**:
- Well-understood problems with clear solutions
- Lower-risk changes
- When you trust the implementation without formal review
- Rapid prototyping

**Steps**:
1. **Plan**: Agent reasons about approach, creates spec at known path
2. **Build**: Agent reads spec, implements creatively

---

### plan_build_review (3 Steps)

**Flow**: `/plan` → `/build` → `/review`

**When to Use**:
- Production-ready code
- Complex implementations
- When quality validation is required
- Team environments

**Steps**:
1. **Plan**: Agent creates specification
2. **Build**: Agent implements the spec
3. **Review**: Agent analyzes quality, outputs PASS/FAIL verdict

**Key Difference**: The review step asks "Is what we built what we planned?" - validating the implementation matches the specification, not just "does it work?"

---

### plan_build_review_fix (4 Steps)

**Flow**: `/plan` → `/build` → `/review` → `/fix`

**When to Use**:
- Maximum autonomy scenarios
- When you want self-healing workflows
- Zero-touch engineering targets

**Steps**:
1-3: Same as plan_build_review
4. **Fix**: Only runs if review returns FAIL, agent resolves issues

---

### Composability Principle

Each step is **deterministic in structure**, **non-deterministic in execution**:

| Step | Deterministic | Non-Deterministic |
|------|---------------|-------------------|
| Plan | Creates spec at known path | Agent reasons about approach |
| Build | Reads spec, creates files | Agent implements creatively |
| Review | Outputs PASS/FAIL verdict | Agent analyzes quality |
| Fix | Only runs if FAIL | Agent resolves issues |

### Core Concept: Agents That Actually Learn

**The Problem**: Traditional software improves as it's used, storing analytics and patterns. Agents of today don't - they forget everything between sessions.

**The Solution**: Agent Experts with ACT → LEARN → REUSE pattern

```
ACT    →  Agent takes a useful action (builds, fixes, answers)
LEARN  →  Agent stores new information in its expertise file
REUSE  →  Agent uses that expertise on the next execution
```

#### 2. Self-Improve Prompt (The Learning Engine)
The workflow that teaches agents HOW to learn:
1. Optionally check git diff for recent changes
2. Read current expertise file
3. Validate against codebase (READ the actual files)
4. Identify discrepancies
5. Update expertise file
6. Enforce line limit (keep it focused)

### The Meta-Agentic Pattern

**Self-Improving Template Meta Prompts**: Prompts that build other prompts, with specific structure, that update themselves with new information.

**Key Insight**: Never update expertise files directly. Teach your agents HOW to learn by updating the self-improve prompt. Let agents maintain their own expertise over time.
